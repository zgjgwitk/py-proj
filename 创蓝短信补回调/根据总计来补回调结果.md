# 根据当月的短信发送成功数据, 修改明细数据以符合对应结果

## 需求描述

### 输入参数

ES地址: `http://192.168.12.124:88/@q1cloud:base.es.biz-10.10.0.8:9200/`

索引名称: `esmsgsms2606`

brandId: `6830`

短信类型: `SERVICE_TYPES`, 例如文本短信 `[1, 2]`, 视频短信 `[5]`

目标成功数: `23335`

目标失败数: `3163`

目标未知数: `214`

## 实现目标

当前 ES 中创蓝短信明细存在部分文档只有发送记录, 回调结果仍为未知状态。

本脚本按 `brandId + 索引 + serviceType` 维度统计文档数量, 并将 `resStatus=1` 的未知文档批量补成成功或失败, 使最终统计数量尽量满足:

- 成功: `resStatus=3`, 数量 `23335`
- 失败: `resStatus=4`, 数量 `3163`
- 未知: `resStatus=1`, 数量 `214`

只允许从 `resStatus=1` 的文档中挑选数据更新, 不修改已经是成功或失败的文档。

## 实现方案

### 1. 脚本配置

建议新建独立脚本, 例如:

`D:\Github\py-proj\创蓝短信补回调\cl_fix_callback_result_by_total.py`

脚本配置项:

```python
ES_HOST = "http://192.168.12.124:88/@q1cloud:base.es.biz-10.10.0.8:9200/"
ES_INDEX = "esmsgsms2606"
BRAND_ID = 6830
SERVICE_TYPES = [1, 2]  # 文本短信: [1, 2], 视频短信: [5]

TARGET_SUCCESS = 23335
TARGET_FAILED = 3163
TARGET_UNKNOWN = 214
TARGET_TOTAL = TARGET_SUCCESS + TARGET_FAILED + TARGET_UNKNOWN

DRY_RUN = True
BATCH_SIZE = 500
BATCH_WAIT_SEC = 1
```

其中 `TARGET_TOTAL` 不作为人工输入参数, 由成功数、失败数、未知数自动计算。

默认先使用 `DRY_RUN=True`, 只打印将要更新的数量和样例文档, 确认无误后再改为 `False` 执行真实更新。

### 2. 前置统计与校验

按 `brandId=6830`、`smsChan=20`（创蓝渠道）和 `SERVICE_TYPES` 查询当前索引数据, 不建议统计整个索引, 避免混入其他品牌、其他渠道或其他短信类型数据。

`SMS_CHAN` 作为脚本配置项, 默认固定为 `20`（创蓝）, 如果后续要复用到其他渠道, 改为可配置即可。

需要统计:

- 当前文档总数: `brandId=6830 AND smsChan=20 AND serviceType IN SERVICE_TYPES`
- 当前成功数: `brandId=6830 AND smsChan=20 AND serviceType IN SERVICE_TYPES AND resStatus=3`
- 当前失败数: `brandId=6830 AND smsChan=20 AND serviceType IN SERVICE_TYPES AND resStatus=4`
- 当前未知数: `brandId=6830 AND smsChan=20 AND serviceType IN SERVICE_TYPES AND resStatus=1`
- 其他状态数: `brandId=6830 AND smsChan=20 AND serviceType IN SERVICE_TYPES AND resStatus NOT IN (1,3,4)`

完整 ES 查询条件示例（以当前统计总数为例）:

```json
{
  "query": {
    "bool": {
      "filter": [
        { "term": { "brandId": 6830 } },
        { "term": { "smsChan": 20 } },
        { "terms": { "serviceType": [1, 2] } }
      ]
    }
  }
}
```

如需按状态细分, 追加 `resStatus` 过滤即可, 例如统计成功数:

```json
{
  "query": {
    "bool": {
      "filter": [
        { "term": { "brandId": 6830 } },
        { "term": { "smsChan": 20 } },
        { "terms": { "serviceType": [1, 2] } },
        { "term": { "resStatus": 3 } }
      ]
    }
  }
}
```

校验规则:

1. 先计算目标总数: `TARGET_TOTAL = TARGET_SUCCESS + TARGET_FAILED + TARGET_UNKNOWN`。
2. 如果当前品牌文档总数 `< TARGET_TOTAL`, 直接退出, 不执行更新。
3. 如果当前成功数 `> TARGET_SUCCESS`, 直接退出, 因为脚本只从未知改成功, 不做反向修正。
4. 如果当前失败数 `> TARGET_FAILED`, 直接退出, 因为脚本只从未知改失败, 不做反向修正。
5. 计算还需要补的数量:
   - `need_success = TARGET_SUCCESS - 当前成功数`
   - `need_failed = TARGET_FAILED - 当前失败数`
   - `need_update_total = need_success + need_failed`
6. 如果当前未知数 `< need_update_total + TARGET_UNKNOWN`, 直接退出。
   - 这样可以保证更新成功/失败后, 至少还能保留 `214` 条未知数据。

### 3. 待更新文档选择策略

只查询满足以下条件的文档:

```json
{
  "bool": {
    "filter": [
      { "term": { "brandId": 6830 } },
      { "term": { "smsChan": 20 } },
      { "terms": { "serviceType": [1, 2] } },
      { "term": { "resStatus": 1 } }
    ]
  }
}
```

总共只需要取 `need_success + need_failed` 条文档。

为了保证每次执行结果可追踪, 查询需要固定排序:

1. 优先按 `reqTime` 升序
2. 再按 `_id` 升序

如果当前 ES 不支持 `_id` 排序或性能较差, 可以改用 `reqTime ASC + gatewayId ASC + toClient ASC`。关键是避免随机取数。

分配规则:

1. 前 `need_success` 条更新为成功。
2. 后 `need_failed` 条更新为失败。
3. 剩余 `resStatus=1` 文档不处理, 作为未知数据保留。

### 4. 更新字段

成功文档更新为:

```json
{
  "resStatus": 3,
  "resStatusCode": "SUCCESS",
  "resStatusMsg": "发送成功"
}
```

失败文档更新为:

```json
{
  "resStatus": 4,
  "resStatusCode": "500",
  "resStatusMsg": "发送失败"
}
```

是否需要同步更新 `resTime`:

- 如果业务只要求修正统计结果, 可以不改 `resTime`, 避免伪造回调时间。
- 如果报表依赖 `resTime`, 建议补成当前执行时间, 但需要在执行前确认。

当前方案默认不更新 `resTime`。

### 5. 批量处理方式

ES 查询使用 `search_after` 分页, 不使用深分页 `from + size`。

每批流程:

1. 查询一批 `resStatus=1` 文档。
2. 根据剩余 `need_success` / `need_failed` 数量构造 bulk update。
3. 执行 ES bulk 更新。
4. 记录本批成功数、失败数、剩余待更新数。
5. 批次间等待 `BATCH_WAIT_SEC`, 降低 ES 压力。

bulk update 条件里建议带上乐观保护:

```json
{
  "doc": {
    "resStatus": 3,
    "resStatusCode": "SUCCESS",
    "resStatusMsg": "发送成功"
  }
}
```

更新前查询已经限定 `resStatus=1`, 但如果担心脚本执行期间状态被其他流程修改, 可以改用 `update_by_query` 或带脚本判断:

```painless
if (ctx._source.resStatus == 1) {
  ctx._source.resStatus = params.resStatus;
  ctx._source.resStatusCode = params.resStatusCode;
  ctx._source.resStatusMsg = params.resStatusMsg;
} else {
  ctx.op = 'noop';
}
```

### 6. 执行后复核

更新完成后再次统计:

- `brandId=6830 AND smsChan=20 AND serviceType IN SERVICE_TYPES` 总数
- `resStatus=3` 数量
- `resStatus=4` 数量
- `resStatus=1` 数量
- 其他状态数量

输出对比:

| 项目 | 目标数量 | 更新前数量 | 更新后数量 |
| --- | ---: | ---: | ---: |
| 成功 resStatus=3 | 23335 | x | x |
| 失败 resStatus=4 | 3163 | x | x |
| 未知 resStatus=1 | 214 | x | x |
| 总数 | TARGET_TOTAL | x | x |

如果更新后结果不等于目标数量, 输出差异并标记执行异常。

### 7. 日志与安全开关

脚本必须输出:

- ES 地址、索引、brandId、smsChan
- SERVICE_TYPES
- 是否 DRY_RUN
- 目标总数和各状态目标数
- 更新前统计
- 计划更新数量
- 每批查询和更新结果
- 更新后统计
- 异常原因

安全开关:

- `DRY_RUN=True`: 只统计和打印计划, 不执行 bulk。
- `MAX_UPDATE_LIMIT`: 可选, 限制单次最多更新数量, 防止配置填错导致大批量误更新。
- 二次确认: 真实执行前打印 `DRY_RUN=False` 的醒目提示。
